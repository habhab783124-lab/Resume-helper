# 功能二：岗位来源与匹配（岗位检索智能体）设计说明

> 对应需求：「希望我们能有一个智能体去网上找适合用户的岗位」
> 对应产品方案：《AI求职与面试平台_20天课程项目方案.md》 3.C 岗位搜索和匹配 / 5 技术选型 / 8 接口草案 / 11 风险兜底

---

## 1. 需求拆解

原需求有两层含义，实现上必须分开处理：

| 层面 | 需求 | 实现 |
|---|---|---|
| 岗位从哪来 | 从网上获取真实岗位 | 可插拔 `JobSource` 数据源 + 聚合去重。**但受合规约束，默认不爬国内招聘站**，见第 4 节 |
| 怎么找得准 | 智能体挑出适合用户的 | ReAct 检索智能体：规划关键词 → 检索 → 观察命中情况 → 换词扩检 → 排序解释 |

产品方案对岗位模块划了两条硬边界，设计全程遵守：

1. **合规边界**：「只使用免登录公开公告或岗位表，不绕过登录」「公开页面可访问不等于自动采集已经获准」；
2. **兜底边界**：「外部站点暂时不可用时，岗位匹配功能仍然可以展示」「提供粘贴岗位描述的入口」。

还有一条产品要求影响文案：**「匹配度用于解释岗位与用户资料的贴合情况，不表示录取概率」**。
这条被固化成了响应里的 `scoreNotice` 字段，前端必须展示。

### 分层原则：core 不依赖框架

这是整个设计里最重要的一条约束。`domain` / `source` / `match` / `agent` / `store` 里
**没有任何 Spring、Jackson、Servlet 的 import**，只依赖 JDK 和 slf4j。

好处：

- 可以用 `JobAgentOfflineDemo` 脱离容器跑完 102 项断言和一次完整智能体流程，几秒钟出结果；
- 队友换 Web 框架、换存储实现都不影响业务逻辑；
- 匹配逻辑的正确性不依赖「Spring 装配对不对」。

代价：需要在 `tools/verify-stubs` 下维护一份 Spring/Jackson 打桩用于本地编译校验（详见第 10 节）。

## 3. 领域模型

| 类型 | 说明 |
|---|---|
| `Job` | 岗位。字段严格对齐产品方案 3.C 的清单：职位名称、公司名称、城市、薪资、学历、经验、技能、岗位描述、来源名称、原始链接、采集时间。另外保留结构化的 `salaryMin/salaryMax/minYears` 用于筛选 |
| `JobQuery` | 检索条件。硬条件（工作类型、年限、薪资、校招）与软维度（城市、关键词）分开 |
| `UserProfileSnapshot` | 用户求职画像快照。**只读消费**，由功能一（材料解析）产出，岗位模块不反向依赖 |
| `JobMatchResult` | 匹配结果：分数、命中技能、缺失技能、理由、差距、各维度得分、AI 解释 |
| `AgentStep` / `AgentRunResult` | 智能体执行轨迹与运行结果 |

### 为什么 `UserProfileSnapshot` 是快照而不是实体

两个模块并行开发，如果岗位模块直接依赖「个人资料」的实体类，接口一改就互相阻塞。
改成不可变快照后，功能一只要在检索时把当前画像拼成这个结构即可，
两边可以各自演进。这也是 `ProfileDto`→`UserProfileSnapshot` 这层转换存在的意义。

### 一个刻意的设计：城市默认是软条件

产品方案说「城市、工作类型和最低年限作为筛选条件」。但我们没有把城市做成默认硬过滤：

- **默认（软条件）**：城市参与打分，不匹配只扣 15 分并给出差距说明，用户能看到「杭州有个很匹配的岗位，但地点不符」；
- **`strictCity=true`（硬条件）**：用户在岗位页勾选「只看上海」时才真正过滤。

理由是求职场景下「知道有个匹配但不在地点范围内的岗位」比「什么都看不到」更有价值。
这个选择通过 `JobQuery.strictCity` 显式暴露给前端，不是隐式行为。

## 4. 数据源：为什么默认不爬招聘网站

原需求是「智能体去网上找岗位」，直觉上应该写爬虫。评估后**主动放弃**，原因：

1. **合规**：Boss直聘、拉勾等站点的服务条款明确禁止自动化采集；产品方案也写明「公开页面可访问不等于自动采集已经获准」；
2. **技术**：反爬强度高（登录态、风控、验证码、动态渲染），维护成本远超 20 天课程项目的预算；
3. **稳定性**：一旦被封 IP，演示当天功能直接失效，而课程项目最怕演示翻车。

于是改成「**合规来源 + 兜底链路**」：

| 来源 | 合规性 | 稳定性 | 状态 |
|---|---|---|---|
| 演示岗位库 | 无风险（人工编造，已标注非真实岗位） | 永不失效 | ✅ 内置 |
| CSV 岗位库 | 无风险（人工整理） | 高 | ✅ 内置 |
| 用户粘贴 JD | 无风险（用户自己复制） | 高 | ✅ 内置 |
| 免登录公开岗位表 | 需逐个确认 robots 与条款 | 中 | ⬜ 预留接口 |
| 搜索引擎 API | 依 API 条款 | 中 | ⬜ 预留接口 |
| 招聘站爬虫 | ❌ 有法律风险 | 低 | ❌ 不做 |

### SPI 设计

```java
public interface JobSource {
    String name();                                  // 展示在前端
    default String kind() { return "public-api"; }  // mock / csv / public-api / search / paste
    default boolean enabled() { return true; }
    default String description() { return name(); }
    List<Job> search(JobQuery query);
}
```

新增来源 = 实现接口 + 注册成 Spring Bean，`JobSourceRegistry` 自动发现，**智能体一行都不用改**。

### 失败的隔离

`JobSourceRegistry` 对每个来源单独 try/catch，任何异常都被收敛成一条 `SourceReport`
（名称、类型、是否成功、命中数、失败原因），返回给前端展示「来源可用性」。
**一个来源挂掉不会让整次检索失败**，也不会让岗位页 500。

## 5. 智能体设计

### 5.1 循环

```text
输入：UserProfileSnapshot + AgentOptions
  │
  ├─ KeywordPlanner.plan(profile)
  │     规则兜底：从目标职位剥掉级别词取方向词，加上前 3 个技能，再补泛化词
  │     「Java 后端开发工程师」→ [后端开发, Java, Spring Boot, MySQL, 软件开发]
  │
  └─ for round in 1..maxRounds:
        prompt = ReActProtocol.userPrompt(画像, 条件, 历史观察, 候选关键词, 已用关键词, 上轮命中数)
        raw    = aiClient.chat(system, prompt)
        action = ReActProtocol.parse(raw)
        if action == finish: 记录轨迹，跳出
        query  = buildQuery(action)            // 关键词 / 城市 / 年限 / 校招
        result = JobSourceRegistry.search(query)
        trace += AgentStep(thought, action, observation)
  │
  ├─ 去重合并
  ├─ 空结果兜底：去掉关键词只按硬条件再查一次
  ├─ MatchScorer 六维打分排序
  └─ JobMatchService 对前 N 个岗位生成 AI 解释
输出：AgentRunResult（岗位 + 轨迹 + 来源报告 + 降级提示）
```

### 5.2 为什么用文本行协议而不是 function calling

提示词协议：

```text
THOUGHT: <一句话思考>
ACTION: search_jobs | import_job | finish
ARGS:
keyword=Java
city=上海
limit=20
```

**决策理由**：需求是「用户自带 token」，意味着模型不固定。
DeepSeek / 通义 / 豆包 / 自建网关的 tool-calling 字段互有差异，
用各家原生 function calling 就要按厂商分支，违背产品方案 5「不直接依赖某个模型厂商的具体请求格式」。

文本协议的优势：
- 在任何 OpenAI 兼容端点上都能工作；
- 解析器对格式宽容（`ACTION:`/`动作:`、`ARGS` 段缺失时回退到正文扫描、也兼容 JSON 输出）；
- **解析失败能干净降级到规则检索**（返回 `AgentAction.UNKNOWN`，用候选关键词列表继续），不会让功能整体挂掉。

### 5.3 三层降级（对应产品方案 11）

| 故障 | 降级行为 | 用户看到 |
|---|---|---|
| 没配 token / 鉴权失败 / 超时 / 限流 | 用 `FakeAiClient` 按规则驱动循环 | `notes` 里说明原因；`aiUsed=false` |
| 关键词过窄，一条都没命中 | `JobSourceRegistry` 放宽为只按硬条件返回 | `notes` + 轨迹里标注「已放宽条件」 |
| 所有来源都失败 | 演示岗位库兜底 | 岗位页仍然有内容，`sourceReports` 标注哪个来源异常 |
| 大模型输出无法解析 | 用 `KeywordPlanner` 的候选词继续检索 | `notes` 里说明 |

**降级不是静默的**：所有降级都会写进 `notes`，前端应原样展示，避免用户以为拿到的是 AI 结果。

### 5.4 离线替身的边界

`FakeAiClient` 是「没有大模型时的确定性规划器」，它**只读取提示词尾部的结构化上下文**
（`---AGENT_CONTEXT---`）来决定下一步动作，并如实标注 `isFallback()=true`。

开发中发现并修掉的一个真实缺陷：最初 `JobMatchService` 也把解释任务交给 `FakeAiClient`，
结果它把 `ACTION: finish` 这种协议文本当成「匹配解释」展示给了用户。
修法是把语义收紧为——`isFallback()` 的客户端只负责驱动检索循环，
**所有自然语言解释必须退回规则文案**。这个 bug 说明「同一接口承担两种语义」是危险的。

## 6. 匹配算法

### 6.1 权重

| 维度 | 权重 | 依据 |
|---|---|---|
| 技能匹配 | 45 | 岗位技能标签 ∪ 岗位描述识别出的技能，对比用户技能 ∪ 经历文本识别出的技能 |
| 岗位方向 | 20 | 目标职位与岗位名称的字符二元组 Dice 相似度 |
| 城市 | 15 | 命中期望城市得满分；岗位未标城市给 60% |
| 经验 | 10 | 岗位最低年限 vs 用户年限 |
| 学历 | 5 | 学历等级（不限 < 大专 < 本科 < 硕士 < 博士） |
| 薪资 | 5 | 岗位薪资上限 vs 期望薪资下限 |

权重放在 `MatchScorer.Weights` record 里，构造时校验总和为 100，改权重只需改一处。

### 6.2 几个刻意的取舍

**经验不做「差一年也算友好」。** 第一版把「岗位要求 1 年、用户 0 年」判成 0.8 分并输出
「经验要求对当前的你比较友好」——这是在骗用户。改成 0.7 分 + 明确提示
「略高于你目前的情况，建议用项目经历弥补」。

**任一侧薪资是「面议」时给中性分（75%），不参与排序竞争。** 避免因为信息缺失造成误排序。

**岗位没标注技能时给中性分（50%）。** 来源信息不全不应该被当成「不匹配」。

**岗位描述里的技能也算数。** 很多岗位只在正文里写「熟悉 Redis」，标签是空的，
所以 `SkillLexicon.extractFrom(job)` 会同时扫描标题、标签和描述。

### 6.3 技能识别的坑

朴素做法（归一化后做子串匹配）会出两类错：

1. **`Java` 命中 `JavaScript`**。归一化后 `"javascript".contains("java")` 为真。
   解法：拉丁文按词切分生成 1~3 元组，在**词元集合**里匹配，`javascript` ≠ `java`。
2. **`多，线程` 被拼成 `多线程`**。
   解法：纯中文别名在「只保留中文、拉丁词替换为分隔符」的字符流上匹配。
3. 另外「http协议」「redis缓存」这类**中英混合别名**在上面两套机制里都匹配不到。
   解法：混合别名走「去掉一切非字母数字的紧凑串」匹配。

三类别名走三条路径，这是 `SkillLexicon.Index` 的核心逻辑，都有对应断言覆盖。

## 7. AI 集成：用户自带 token

### 7.1 优先级

```text
请求头 X-AI-Api-Key / X-AI-Base-Url / X-AI-Model
        ↓ 没有才回落
服务端 application.yml 的 app.job.ai.*（api-key 走 AI_API_KEY 环境变量）
        ↓ 都没有
FakeAiClient（规则检索 + 规则解释）
```

这样同时满足了两条约束：
- 产品方案 5「密钥放在后端配置中，不能写进前端代码」——服务端兜底 key 用于课程演示；
- 实际需求「让用户填自己的 token」——请求头覆盖服务端配置。

### 7.2 为什么客户端必须按请求构造

`AiClientResolver` 每次调用都 `new OpenAiCompatibleAiClient(...)`，**没有注册成 Spring 单例**。

原因：如果带密钥的客户端是单例，多个用户并发时就会出现
「A 用户的请求用了 B 用户的 key」。这类串号 bug 在演示时极难复现、极难排查。

`JobService` / `JobSearchAgent` 因此都**不持有 `AiClient` 字段**，而是作为方法参数传入。
这是「无状态单例服务 + 有状态请求对象」的标准做法。

### 7.3 密钥不落日志

`AiCredentials.maskedKey()`（形如 `sk-a***xyz`）是唯一允许进日志的形式。
`GlobalExceptionHandler` 也只回传异常类型和业务消息，不把堆栈或 payload 泄给前端。

### 7.4 HTTP 客户端

用 JDK 自带的 `java.net.http.HttpClient`，不引第三方 SDK：

- 无额外依赖，不受 SDK 版本兼容问题影响；
- 静态 `HttpClient` 负责连接复用（线程安全），密钥随请求对象回收；
- 状态码翻译成中文可读提示，并区分**是否值得重试**：
  - 401/403 → 「API Key 无效或没有该模型权限」，`retryable=false`
  - 404 → 「模型或接口路径不存在，请检查 base-url 与 model」，`retryable=false`
  - 429 / 5xx / 超时 → `retryable=true`

## 8. 接口契约

见 `backend/README.md` 第 3 节。核心约定：

- 路径沿用产品方案 8 的草案（`GET /api/jobs`、`POST /api/jobs/import`、`POST /api/jobs/{id}/match`）；
- 响应统一 `{success, message, data}`；
- `JobCard` 字段与前端原型 `prototype-static/assets/app.js` 的 mock 对象逐一对齐
  （`id/title/company/mark/style/salary/place/experience/tags/score/reason`），
  前端替换数据源即可，渲染逻辑不用改；
- 响应固定带 `scoreNotice`，提醒「匹配度不是录取概率」。

## 9. 关键决策一览

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 岗位来源 | 演示库 + CSV + 粘贴 JD，SPI 预留真实来源 | 直接爬 Boss直聘 | 合规风险 + 反爬成本 + 演示稳定性 |
| 智能体动作格式 | 文本行协议 | 各厂商 function calling | 用户自带 token ⇒ 模型不固定 |
| AI 客户端生命周期 | 按请求构造 | Spring 单例 | 避免用户间 token 串号 |
| 城市筛选 | 默认软条件 | 默认硬过滤 | 让用户看到「匹配但地点不符」的信息 |
| 存储 | 内存实现 + 预留 JPA | 一开始就上 MySQL | 岗位模块不被队友的数据库进度阻塞 |
| 分层 | core 零框架依赖 | 全部用 Spring 注解 | 业务逻辑可脱离容器秒级验证 |
| 流式推送 | 同步返回轨迹 | SSE 边跑边推 | 降低不可测的异步复杂度；`trace` 已够前端渲染时间线 |
| 智能体轨迹 | 返回给前端 | 只写日志 | 「让用户看见智能体在做什么」是产品体验的一部分 |

## 10. 验证方式

### 10.1 离线自检

`src/test/java/.../JobAgentOfflineDemo.java` 是**可执行的规格说明**，覆盖 8 组共 **102 项断言**：

| 组 | 覆盖内容 |
|---|---|
| 1 | 薪资解析（`15-22K` / 全角连字符 / `1.5-2.5万` / `24万/年` / 面议）、经验年限解析、学历等级、标题相似度 |
| 2 | 技能词典：`Java` 不误命中 `JavaScript`、`spring-boot` 归一、中文技能、不跨标点拼假技能、中英混合别名 |
| 3 | 粘贴 JD 解析：标题/公司/城市/行政区/薪资/学历/校招/技能 |
| 4 | CSV 来源：`\|` 分隔技能、带逗号的引号字段、文件缺失不抛异常 |
| 5 | 智能体端到端：轨迹、关键词、来源调用、降级标注、分数降序 |
| 6 | 差距报告：分数、经验差距、缺失技能、可执行建议、不出现「录取概率」 |
| 7 | 存储与收藏：幂等收藏、用户隔离、空 userId 不落库 |

第 8 组是关键补充：`JobService` 的构造参数全是普通对象，`JobViews` 只有 record 和静态工厂，

那部分交给 `tools/smoke-api.ps1` 做 HTTP 冒烟。

### 10.2 编译期打桩

`tools/verify-stubs` 下有一份 Spring / Jackson / Jakarta 的**最小类型打桩**（35 个文件），
只声明本项目用到的注解和方法签名。用途是在没有 Maven、装不了依赖的机器上，
让 `javac` 能把**整份后端（77 个文件）**编译一遍，从而类型检查控制器、服务、DTO、配置。

打桩不参与 Maven 构建（在 `src/main/java` 之外），打包不会带上。

**这个做法当场就抓到了 3 个真实缺陷**（见下节 #1~#3），所以留下来作为常规校验手段。

打桩的风险是「它可能和真实 API 不一致，给出虚假的通过」。因此后来在能联网的机器上
补做了下面的真实构建验证，确认打桩是忠实的。

## 11. 开发中发现并修掉的问题

这些是本地编译 / 自检真正报出来的，不是事后编的：

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | `MatchScorer` 一构造就抛「权重之和必须为 100，当前为 0」 | **record 紧凑构造器陷阱**：校验里调用了实例方法 `total()`，但 record 字段在紧凑构造器执行完之后才赋值，此时读到的全是默认值 0 | 紧凑构造器里用**参数**求和，不用实例方法 |
| 2 | `AiException` 编译不过 | 只定义了 `(String)` 和 `(String,boolean,Throwable)`，而客户端调用的是 `(String, boolean)` | 补构造器 |
| 3 | `ProfileDto.toSnapshot()` 编译不过 | `Builder.industries` 只有 varargs 版本，传 `List` 无法匹配 | 补 `industries(List)` 重载 |
| 4 | 智能体运行时 NPE | `cond ? action.intArg(..) : options.maxMinYears()` —— 三元表达式里 `int` 和 `Integer` 会做数值提升，为 null 的 `Integer` 被自动拆箱 | 改成显式 `if` 赋值 |
| 5 | `JobQuery.city()` NPE | 查询对象字段默认为 null，任何 `.isEmpty()` 都会炸 | 字段给空串默认值 |
| 6 | `SkillLexicon.Index` 中文识别错乱 | `Character.isLetterOrDigit('多')` 为 true，中文被当成拉丁词元累加；`http协议` 这类混合别名永远匹配不上 | 拉丁词元限定 ASCII；索引拆成「词元集合 / 纯中文字符流 / 紧凑串」三条匹配路径 |
| 7 | 粘贴 JD 解析出「上海 · 上海徐汇区」 | 行政区正则把城市名一起吃了进去 | 匹配后剥掉已识别的城市前缀 |
| 8 | 应届生投「1-3 年」岗位被判成「经验要求友好」 | 打分曲线过于宽松（`need <= have + 1` 给 0.8） | 改为 0.7 并明确提示差距，不让文案误导用户 |
| 9 | 匹配解释里出现 `ACTION: finish` | `FakeAiClient` 同时被当成「检索规划器」和「解释生成器」 | 收紧语义：`isFallback()` 的客户端只驱动检索，解释一律退回规则文案 |
| 10 | `smoke-api.ps1` 报出一堆分散的语法错误（行号互相矛盾） | 宿主是 **Windows PowerShell 5.1**（不是 pwsh 7），它把无 BOM 的 UTF-8 文件按 ANSI 解码，中文注释被拆成非法 token；用正确的 UTF-8 解码后解析零错误 | 给所有 `.ps1` 加 **UTF-8 BOM**；`.sh` 必须保持**无 BOM**（否则 shebang 失效） |
| 11 | 冒烟测试里所有中文断言全部失败，岗位名显示成 `å²ä½åº` | 服务端返回的是**合法 UTF-8**（`Content-Type: application/json`，符合 JSON 规范），是 PS 5.1 的 `Invoke-RestMethod` 在缺 charset 时按 ISO-8859-1 解码 | 脚本改为取原始字节自行按 UTF-8 解码；同时让服务端显式声明 `charset=UTF-8`，照顾宽容度差的客户端（浏览器/axios 本来就没问题） |
| 12 | 「收藏列表包含该岗位」断言失败，但紧接着用同一份数据判断的「saved=true」却通过 | PS 5.1 的 `ConvertFrom-Json` 会把**单元素数组拆成标量**，此时直接取 `.Count` 不可靠 | 脚本统一用 `CountOf`（内部 `@()` 包一层数组）做计数 |

第 1、4、5、8、9 条属于「不跑起来根本发现不了」的问题；
第 10~12 条属于「不按目标环境的实际解释器/客户端跑一次就发现不了」的问题——
第 11、12 条尤其说明：**验证脚本本身也是代码，它会有自己的 bug，
而且它的 bug 会伪装成"被测代码有 bug"**，必须先用已知正确的响应把它校准一遍。

共同结论是：坚持 core 层零框架依赖、维护离线自检、给脚本做语法与编码校验，
以及在真实环境（真实 Maven + 真实 Spring Boot + 真实 HTTP）里跑一遍，缺一不可。
